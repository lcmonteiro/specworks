# Refinement: add-reopen-change

## Problem

After `specworks close`, a change is archived with its specs already merged into the living docs. The change is then sent to CI and to review, where a check can fail, a reviewer can ask for something different, or the PR can conflict. Today the only way back is a new change, which loses the history, repeats the process and leaves the original name taken. The feedback can also change what is wanted, not only the code.

## Outcomes

- `specworks reopen --change <ref> --reason "<why>" --phase <phase>` moves an archived change back to the active changes, with its name and files intact, and clears its `done` state. The reason is mandatory and comes from the user.
- A reopened change starts in the phase the problem needs: `refine` (goal, outcomes or scope changed), `specify` (requirements or criteria wrong), or `review` (code, tests or design: the problem becomes an open finding that `/specworks-build` acts on).
- `/specworks-reopen` takes the problem from the user (or asks for it), decides the phase, says it in one line and asks for confirmation before running the command.
- The reopened change can be closed again: its delta specs update the living spec in place, and `requirements.md` History shows both closes.
- A change that is not archived, or was abandoned, is refused with a clear message.

## Context

**Observed:**
- `close_change` (`src/specworks/specs/merge.py`) writes the living `spec.md` and `requirements.md`, then moves the folder to `<archive>/<date>-<name>/` and sets `phase: done`. `abandon` makes the same move without merging.
- `create_change` (`src/specworks/core/changes.py`) refuses a name that was archived. `status` and `telemetry push` read archived changes through `resolve_archived` (`src/specworks/cli/output.py`).
- `specworks phase` only works on active changes; `done` can only be set by close (REQ-PROJ-011).
- Moving the folder back is not enough: the check rejects an ADDED ID already in the living spec (REQ-SPECS-006), and the merge rejects it too (`apply_delta`, REQ-SPECS-013).
- `requirements.md` History lines name the change that merged each ID (`HISTORY_LINE_RE`, `retired_ids`, `modified_since` in `src/specworks/specs/capabilities.py`), so the check can tell an ID this change added from another change's.
- Findings route to `specify` at the earliest (`FINDING_STEPS`, `spec-gap` in `src/specworks/workflow/review.py`); there is no `refine` step. The review gate needs no open finding, and `/specworks-build` derives its cycle from the open findings (REQ-FLOW-010, 011, 012, 016).
- Close commits on the change's own branch (`branch_per_change`); the capabilities touched are `project`, `specs`, `workflow` (skills) and `cli`.

**Assumed:**
- The reopen happens on the change's own branch, with the PR still open or just merged; the user manages git (switch, rebase, push).
- History lines are generated by close and never edited by hand, so they can be trusted to attribute an ID to a change.

## Constraints

- [hard] Only `specworks close` writes the living docs; reopen does not touch them.
- [hard] The reason is required and non-empty, never invented by the skill.
- [hard] IDs are never renumbered or reused; a different change's ID still collides as today.
- [hard] CLI errors are values (`{"error": ...}`, exit 1 under `--json`); text is read and written as UTF-8.
- [hard] Coverage stays at 95% on every OS.
- [soft] No dependency on git history, so it works after a squash, a rebase or a shallow clone.
- [soft] The skill follows the shared stops: one closing question per stop.

## Options

### Option A: Re-merge in place

Reopen moves the folder back and records the reason; the living docs stay as the first close left them. `specworks check` and the merge treat an ID that History attributes to this change as its own: an ADDED block already in the living spec is replaced in place, a REMOVED ID already gone is skipped, and History gets a second line for the same change.

- **Pros:** works after a squash, rebase or conflict; no git; the deltas stay valid as written; History keeps both closes; reopen writes no living doc.
- **Cons:** changes two rules in `specs` (check and merge) and must keep other changes' IDs strict; the wording of the second History line must be decided.
- **Effort:** M
- **Touches:** project, specs, cli, workflow (skill)
- **Outcomes:** meets all.

### Option B: Unmerge on reopen via git

Reopen moves the folder back and reverses the merge in the living docs: removes the ADDED blocks, restores the MODIFIED and REMOVED ones from the commit before the close, and drops the History line.

- **Pros:** the deltas are valid as written and the second close is an ordinary close.
- **Cons:** needs the close commit and its parent, so it fails after a squash, a rebase with a reworded subject or a shallow clone; it can erase another change's later edit; a second writer of the living docs; hard to make all-or-nothing across capabilities.
- **Effort:** L
- **Touches:** project, specs, cli, workflow (skill)
- **Outcomes:** meets the move and the second close only while the history is intact; fails the "survives a conflict" case.

### Option C: Move only, rewrite by hand

Reopen only moves the folder and records the reason; `/specworks-specify` rewrites each ADDED block as MODIFIED and drops each REMOVED block by hand.

- **Pros:** the least code.
- **Cons:** History says MODIFIED for what was an addition; a forgotten block fails with a confusing "already exists" error; the rules live only in skill text.
- **Effort:** S
- **Touches:** project, cli, workflow (skill)
- **Outcomes:** meets the move and the reason, but the second close is error-prone and History loses its truth.

## Recommendation

Option A (agreed with the user): it is the only one that works in the situations that cause a reopen (rebase, squash, conflict) and it keeps the deltas and History true.

## Open Questions

- The wording of the second History line (a repeated `ADDED`, or a marker such as `(reopened)`). (who can answer: decided in specify, with the user)
- `status` lists every past reopen, or only the latest. (who can answer: decided in specify, with the user)

## Candidate Capabilities

- `project`: modified - reopen an archived change back to active (a `reopened` record with date, reason and phase), refusing a change that is active, abandoned or missing.
- `specs`: modified - check and merge treat an ID that History attributes to the same change as its own (ADDED replaced in place, REMOVED already gone skipped).
- `cli`: modified - the `reopen` command (`--change`, `--reason`, `--phase`, `--json`), and `status` shows the reopen record.
- `workflow`: modified - `/specworks-reopen` skill decides the phase from the problem; the reason becomes a finding when it starts at `review`.
