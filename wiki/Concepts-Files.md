# Files: changes and living docs

```text
spec.yml                                  # config (named after the workflow folder: spec/)
spec/changes/<change>/                    # one folder per change in flight
  .change.yaml                            # name, created, phase, specified (fingerprints)
  refinement.md                           # refine
  proposal.md                             # specify: why, what, which capabilities
  specs/<capability>/spec.md              # specify: delta spec (ADDED / MODIFIED / REMOVED)
  design.md                               # specify (decisions), design (Interfaces)
  diagrams/<name>.d2 + .svg               # specify/design: D2 source and rendered SVG
  tasks.md                                # specify: checklist; ticked in design/test/code
  traceability.md                         # generated by `specworks trace --write`
  review.md                               # review: findings and decisions
spec/changes/archive/<date>-<change>/     # closed or abandoned changes
<capability path>/docs/                   # living docs, next to the code
  spec.md                                 # merged by `specworks close`
  requirements.md                         # index + History, generated by `specworks close`
  design.md, architecture.md, diagrams/   # written by /specworks-close
```

The config file is named after the workflow folder: `specworks init --dir
spec` creates `spec.yml` and `spec/`. The default is `specworks.yml` +
`specworks/`. The file starts with `specworks: 1`, which marks it as a
specworks config.

## Delta specs and living specs

A **delta spec** says what one change changes, per capability, at
`<dir>/changes/<change>/specs/[<module>/]<capability>/spec.md`. The **living
spec**, `<capability path>/<docs_dir>/spec.md`, says what the system does now.
`specworks close` applies the delta to the living spec:

| Delta section | Effect on the living spec |
|---|---|
| `## ADDED Requirements` | appended |
| `## MODIFIED Requirements` | the block with the same ID is replaced in place |
| `## REMOVED Requirements` | the block is deleted (its ID is retired forever) |

## `.change.yaml`

```yaml
name: add-short-links
created: '2026-10-17T19:55:11'
phase: design
specified:
  REQ-LINK-001: 0f0b38da1971
  REQ-LINK-002: 04c19f6ab6af
```

`specified` is written when `start` passes the specify gate: one fingerprint
per requirement. Later gates compare the specs with it and warn when one
changed, was added or was dropped (see [Change 2: modifying a capability with a living spec](Tutorial-Modify)).
`skip_specs: true` and `abandoned: <reason>` appear when they apply.

## Modules (sub-projects)

Like git submodules, a project can link other folders that have their own
config. Each module is a complete project (own context, capabilities and
changes):

```text
repo/
  spec.yml                # top level: lists billing
  spec/changes/           # cross-module changes
  services/billing/
    spec.yml              # module: lists tax
    spec/changes/         # billing's own changes
    src/invoices/docs/    # living docs of billing:invoices
    tax/spec.yml          # nested module billing/tax
```

- `specworks module add <path>` creates and links a module.
- Every module uses the same config and folder name as the top level (set once
  by `specworks init --dir ...`): `spec.yml` + `spec/` everywhere. A module with
  another name (e.g. `docs.yml`) is an error that says what to rename.
- A listed module whose folder has no config (e.g. a git submodule not checked
  out) shows up under `missingModules` in `specworks context`.
- Commands act on the **nearest** module; `--all` shows the whole workspace.
- Context is **inherited**: top level first, then each module down to the
  current one.
- Capabilities and changes of other modules are named `module:name`
  (`billing:invoices`, `analytics:track-clicks`).

Example: [`specworks module add` / `module list`](CLI-Project#specworks-module-add--module-list).
