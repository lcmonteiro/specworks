# integrations

## Purpose

Integrations with outside tools: rendering design diagrams from D2 sources to
SVG with one shared look, and installing the packaged agent skills for the AI
tools a project uses (Claude Code, GitHub Copilot).

## Requirements

### Requirement: REQ-INTEG-001 Rendering diagrams

The system SHALL render each `diagrams/*.d2` source of a folder to an SVG next
to it, with the workspace's diagram settings (theme, dark theme, layout, sketch,
pad, and no d2 version). Each SVG SHALL carry a stamp with a hash of its source
and settings, right after the XML declaration when there is one.

#### Scenario: AC-INTEG-001.1 A stamped SVG

- **WHEN** a change's diagrams are rendered
- **THEN** each SVG starts with the stamp (after `<?xml …?>`) and was rendered with the workspace's settings (`--theme=0 --layout=elk --pad=24 --omit-version --dark-theme=200` by default)

#### Scenario: AC-INTEG-001.2 Themes by name or number

- **WHEN** the theme and dark theme are given by name, by number, or the dark theme as `none`
- **THEN** the render uses the matching theme numbers, and no dark theme for `none`

#### Scenario: AC-INTEG-001.3 Stable render options

- **WHEN** the default settings, or sketch with no dark theme, are turned into render options
- **THEN** they are exactly the documented flags, so committed SVGs don't all turn stale

#### Scenario: AC-INTEG-001.4 With the real d2

- **WHEN** a diagram is rendered with pyd2's d2
- **THEN** the SVG holds the stamp and the diagram's labels

### Requirement: REQ-INTEG-002 Diagram state

The system SHALL report each diagram as `ok` when its SVG's stamp matches the
current source and settings, `missing` when it has no SVG, and `stale`
otherwise (an edited source, changed settings, or an SVG not generated by
specworks). Checking SHALL not need d2.

#### Scenario: AC-INTEG-002.1 An edited source

- **WHEN** a rendered diagram's source changes
- **THEN** it is `stale` until it is rendered again

#### Scenario: AC-INTEG-002.2 Changed settings

- **WHEN** a render setting (e.g. sketch) changes
- **THEN** the diagram is `stale`, and rendering it again applies the setting

#### Scenario: AC-INTEG-002.3 A hand-edited SVG

- **WHEN** the SVG was written by hand (no stamp)
- **THEN** the diagram is `stale`

#### Scenario: AC-INTEG-002.4 A theme renamed to its number

- **WHEN** the configured theme changes from a name to its number
- **THEN** the diagram stays `ok`

#### Scenario: AC-INTEG-002.5 Checking without d2

- **GIVEN** no d2 is available
- **WHEN** diagrams are checked
- **THEN** the state is reported (`missing`) and no SVG is written

### Requirement: REQ-INTEG-003 The d2 that renders

The system SHALL render with the d2 that pyd2 provides (its pinned release),
or with the program named by `SPECWORKS_D2` when that is set. A missing d2, a d2
that doesn't run, a d2 compile error, and an SVG that d2 wrote but that can't be
read or stamped SHALL each be reported as an error naming the diagram, never as
a crash.

#### Scenario: AC-INTEG-003.1 Which d2

- **WHEN** `SPECWORKS_D2` is set, or not
- **THEN** it is used, or pyd2's d2 is, whose `--version` is pyd2's pinned release

#### Scenario: AC-INTEG-003.2 No d2, or one that doesn't run

- **WHEN** pyd2 has no binary, or `SPECWORKS_D2` names a program that doesn't run
- **THEN** rendering fails with `cannot render <name>.d2: …`, and the d2 is reported as missing when there is none

#### Scenario: AC-INTEG-003.3 A d2 error

- **WHEN** d2 fails to compile a source
- **THEN** the error d2 printed is reported for that diagram

#### Scenario: AC-INTEG-003.4 An SVG that can't be stamped

- **WHEN** d2 succeeds but writes an SVG whose `<?xml` declaration never closes, or one that isn't UTF-8, or writes no SVG at all
- **THEN** that diagram fails, with `cannot render <name>.d2: …` for the first two and d2's own `… no SVG was written …` message naming it for the third; the other diagrams of the run still render, and the command exits 1

### Requirement: REQ-INTEG-004 Choosing the AI tools

The system SHALL install skills for the tools given as `auto` (the tools the
project already uses, or every tool when none is detected), `all`, or a comma
list of tool IDs (`claude`, `copilot`). An unknown tool, or an empty list, SHALL
be refused before anything is written.

#### Scenario: AC-INTEG-004.1 Nothing detected

- **WHEN** a project that uses no supported tool is initialised
- **THEN** skills are installed for Claude Code and Copilot

#### Scenario: AC-INTEG-004.2 Detected tools

- **WHEN** the project has `.github/copilot-instructions.md`, or `CLAUDE.md`
- **THEN** skills are installed only for that tool

#### Scenario: AC-INTEG-004.3 Unknown tool

- **WHEN** an unknown tool (e.g. `cursor`) is given
- **THEN** the command fails with `unknown tool 'cursor'` and nothing is written

#### Scenario: AC-INTEG-004.4 No tool

- **WHEN** the tool list is empty (e.g. `,`)
- **THEN** it is refused with `no tool given`

### Requirement: REQ-INTEG-005 Installing the skills

The system SHALL write every packaged skill, with its shared parts filled in, to
each chosen tool's skills folder (`.claude/skills/<name>/SKILL.md`,
`.github/skills/<name>/SKILL.md`), keeping only the frontmatter keys that tool
understands. For Copilot, it SHALL also write a prompt file per skill
(`.github/prompts/<name>.prompt.md`) holding the description, agent mode and the
skill's instructions. In the same folders, it SHALL remove every skill folder and
prompt file named `specworks-…` (or the older `sw-refine`) that is no longer
shipped, report each removal, and leave every other name alone. Skills always
go to the workspace root and are refreshed by `specworks skills`.

#### Scenario: AC-INTEG-005.1 Every skill

- **WHEN** skills are installed for all tools
- **THEN** every packaged skill, each named `specworks-…`, is in each tool's folder, with a Copilot prompt file

#### Scenario: AC-INTEG-005.2 Frontmatter per tool

- **WHEN** skills are installed for Copilot, or for Claude Code
- **THEN** Copilot's copy keeps `name` and `description` but not `allowed-tools`; Claude Code's keeps `allowed-tools`

#### Scenario: AC-INTEG-005.3 Copilot prompt files

- **WHEN** skills are installed for Copilot
- **THEN** each prompt file's frontmatter has the description and `agent: agent` and no `name`, followed by the skill's instructions

#### Scenario: AC-INTEG-005.4 Shared parts

- **WHEN** skills are installed
- **THEN** no installed file keeps a `specworks:include` marker; the shared text is in its place

#### Scenario: AC-INTEG-005.5 Where and when

- **WHEN** a module is initialised, or `specworks skills` runs for another tool
- **THEN** the module gets no skills folder of its own, and the refresh writes the other tool's skills

#### Scenario: AC-INTEG-005.6 Skills that are no longer shipped

- **GIVEN** a project whose `.claude/skills/` and `.github/` hold `specworks-propose` and `sw-refine` (skill folders and Copilot prompt files) and a user's own `my-skill`
- **WHEN** `specworks skills --tools all` runs
- **THEN** the stale `specworks-propose` and `sw-refine` folders and prompt files are removed, each printed as `removed <path>`, and `my-skill` and every shipped skill are kept
